# 特性规格：Streaming RPC（流式调用：服务端流 / 客户端流 / 双向流）

**Feature Branch**: `004-streaming-rpc`

**Created**: 2026-09-13

**Status**: Draft

**Input**: 用户描述："支持 client side stream 和 server side stream 的 rpc，同样要兼容 gRPC。"

## 用户场景与测试（User Scenarios & Testing）

### User Story 1 - 服务端流式方法（server streaming） (Priority: P1)

服务端发布一个「单请求 → 响应消息序列」的方法：客户端发送一条请求后，
服务端按业务逻辑产出零条或多条响应消息，按发送顺序逐一送达客户端，最后
以正常状态（OK）或错误状态结束本次调用。客户端在流结束前持续收到消息，
并能区分「流正常结束」与「流以错误终止」。

**Why this priority**: 服务端流是最常用的流式形态（推送、批量下发、
订阅类场景的基础），且在 HTTP/2 语义上是三条路径中最先打通「一条流上
多消息」的切片，为后续形态复用全部基础设施。

**Independent Test**: 启动仅含一个服务端流式方法的服务端，客户端发送
一条请求，验证按序收到全部响应消息且流以正确状态结束。

**Acceptance Scenarios**:

1. **Given** 服务端已注册服务端流式方法且将返回 5 条响应，**When**
   客户端发送一条请求，**Then** 客户端按发送顺序收到 5 条响应，随后
   流以 OK 状态正常结束。
2. **Given** 服务端流式方法决定返回零条响应，**When** 客户端发送请求，
   **Then** 客户端立即收到流结束（OK），不误报错误。
3. **Given** 服务端流式方法在中途以非 OK 状态终止，**When** 客户端
   正在接收，**Then** 客户端收到已送达的部分消息后收到该错误状态，
   不会无限等待。

---

### User Story 2 - 客户端流式方法（client streaming） (Priority: P1)

服务端发布一个「请求消息序列 → 单响应」的方法：客户端连续发送零条或
多条请求消息，随后声明「发送完毕」（半关闭）；服务端逐条读取请求消息，
在客户端半关闭后产出一条响应并结束调用。客户端可全程感知服务端是否
提前以错误终止。

**Why this priority**: 客户端流覆盖上传/聚合类场景（批量上报、分块
传输），与用户点名的两类流式形态之一；wire 侧与服务端流共享帧序
列机制，但 API 形态（读侧在服务端、写侧在客户端、半关闭语义）独立
可测。

**Independent Test**: 启动仅含一个客户端流式方法的服务端，客户端发送
N 条请求后半关闭，验证服务端恰好收到 N 条（顺序一致）并返回唯一响应。

**Acceptance Scenarios**:

1. **Given** 服务端已注册客户端流式方法，**When** 客户端发送 10 条
   请求后声明发送完毕，**Then** 服务端按序收到 10 条请求并返回一条
   响应，客户端正常收到该响应。
2. **Given** 客户端未声明发送完毕，**When** 服务端流式方法试图提前
   完成调用，**Then** 调用按框架定义的语义结束（服务端主动收流），
   客户端收到响应，不产生悬挂。
3. **Given** 客户端发送零条请求即声明发送完毕，**When** 服务端方法
   处理空请求序列，**Then** 调用正常完成，服务端正确观察到「零条
   请求」。

---

### User Story 3 - 双向流式方法（bidirectional streaming） (Priority: P2)

服务端发布一个双向流方法：同一调用上，客户端与服务端各自独立地按自己
的节奏收发消息序列，互不等待对方结束；任一方都可以先完成自己的发送
（半关闭）而继续接收。

**Why this priority**: 双向流是前两种形态的组合，gRPC 四种调用形态的
最后一块；用户明确点名的是 client/server 两类流，双向流作为自然延伸
排在其次。实现上复用 US1/US2 的全部机制，增量在 API 并发收发语义。

**Independent Test**: 启动仅含一个双向流方法的服务端，客户端与服务端
交替收发消息（服务端对每条请求回一条响应但整体交错），验证双方序列
完整、顺序一致、双方各自正常收尾。

**Acceptance Scenarios**:

1. **Given** 服务端已注册双向流方法，**When** 客户端与服务端各自独立
   交错发送多条消息，**Then** 双方各自按序收齐对方的消息，调用以 OK
   状态结束，无死锁、无消息错乱。
2. **Given** 客户端已半关闭但仍在接收，**When** 服务端继续发送剩余
   响应，**Then** 客户端仍能完整收到半关闭之后送达的消息。

---

### User Story 4 - 工具生成流式类型化接口 (Priority: P2)

开发者在 proto 中用 `stream` 关键字声明方法后，代码生成工具为服务端
生成带流式参数的服务接口方法（延续既有「继承接口 + 注册实例」的服务
端形态），为客户端生成与既有代理形态一致的流式调用入口；请求/响应
消息保持强类型。一元方法的既有接口与代理完全不变。

**Why this priority**: 类型化接口是 003 已确立的最终接口形态；流式
若绕开它将产生两套并存的编程模型，用户价值打折。但它依赖 US1/US2 的
能力先行验证，故排在 P2。

**Independent Test**: 对含三种流式方法的 proto 执行代码生成，编译
一个实现全部流式方法的服务端与一个调用全部流式方法的客户端，验证
签名、类型与既有形态一致且无需手写胶水。

**Acceptance Scenarios**:

1. **Given** proto 中声明了服务端流式方法，**When** 执行代码生成并
   编译，**Then** 服务端接口出现对应的可重写方法，客户端代理出现
   对应的流式调用入口，二者消息类型均为生成的强类型消息。
2. **Given** 既有 proto 未使用 `stream` 关键字，**When** 使用新版
   工具重新生成，**Then** 生成结果与 003 版本兼容，既有用户代码
   无需修改即可编译。

### User Story 5 - 与官方 gRPC 流式互通 (Priority: P2)

以官方 gRPC 实现作为对端：官方客户端调用 urpc 服务端的三种流式方法、
urpc 客户端调用官方服务端的三种流式方法，消息序列、顺序、半关闭、
结束状态全部符合 gRPC 语义。

**Why this priority**: 线协议兼容是宪法原则 I（不可妥协），流式互通
是本特性「兼容 gRPC」验收的执法机制；但其验证形态复用一元互通已建
成的对端测试基建，属于对 US1–US3 正确性的外部确认。

**Independent Test**: 运行流式互通测试脚本（官方 gRPC 对端），两个
方向 × 三种流式形态全部通过。

**Acceptance Scenarios**:

1. **Given** urpc 服务端注册三种流式方法，**When** 官方 gRPC 客户端
   依次调用，**Then** 各形态消息序列与结束状态符合 gRPC 语义。
2. **Given** 官方 gRPC 服务端实现三种流式方法，**When** urpc 客户端
   依次调用，**Then** 结果同上。

---

### User Story 6 - 流式调用的取消、截止时间与流控语义 (Priority: P2)

取消、截止时间与流控行为对三种流式形态均生效且与 gRPC 对齐：客户端
可随时取消在途流式调用；服务端处理器可提前以错误终止；截止时间约束
从发起到流结束的全程；接收方消费不及时时，发送方必须暂停而非无界
缓冲；流上消息严格按发送顺序投递。

**Why this priority**: 这些语义决定流式调用在生产环境的可用性（防止
内存失控、悬挂调用），是「兼容 gRPC」的组成部分；但可以在三种基本
形态打通之后并行补齐。

**Independent Test**: 分别构造取消、超时、慢消费三类场景的自动化
测试，验证状态码、资源释放与背压行为。

**Acceptance Scenarios**:

1. **Given** 客户端正在接收服务端流，**When** 客户端取消调用，
   **Then** 调用以 CANCELLED 结束，服务端处理器观察到取消并可提前
   停止产出，不继续向已取消的流写入。
2. **Given** 流式调用设置了截止时间，**When** 流未在截止时间内完成，
   **Then** 调用以 DEADLINE_EXCEEDED 结束，双方资源被释放。
3. **Given** 接收方长时间不读取消息，**When** 发送方持续尝试发送
   超过流控窗口的消息量，**Then** 发送方暂停投递（内存占用有界，
   不随消息总数无界增长），接收方恢复读取后继续投递且顺序不乱。

---

### User Story 7 - 流式示例与性能基线 (Priority: P3)

框架提供可独立构建运行的流式端到端示例（覆盖三种形态），并提供
流式吞吐/时延基准，纳入既有基准体系，可跨版本对比。

**Why this priority**: 示例与基准是采用体验与性能治理的配套交付，
不阻塞核心能力。

**Independent Test**: 按示例说明构建并运行流式示例；运行流式基准并
得到可留档的吞吐数据。

**Acceptance Scenarios**:

1. **Given** 全新环境，**When** 按示例说明构建运行流式示例，
   **Then** 三种形态各自完成一轮端到端调用并输出可观察的结果。
2. **Given** 基准套件，**When** 运行流式基准，**Then** 输出消息
   吞吐与端到端时延统计，可重复运行。

### Edge Cases

- 客户端在服务端仍在发送时取消 → 服务端写侧观察到失败/取消，不再
  投递后续消息，资源释放。
- 客户端流式调用中服务端在客户端半关闭前以错误终止 → 客户端停止
  发送并收到错误状态，不悬挂。
- 空流：客户端流零请求即结束；服务端流零响应即结束——均不视为错误。
- 单条消息跨越多个 HTTP/2 DATA 帧（超大消息）→ 消息边界仍正确。
- 流控窗口耗尽 → 发送暂停、恢复后继续，顺序与完整性不变。
- 截止时间在流中途到期 → 已送达消息保留，调用按 DEADLINE_EXCEEDED
  终止。
- 单连接上并发多条流式调用与其他一元调用复用 → 互不干扰。
- 服务端优雅关闭时存在在途流 → 停止接收新调用，在途流按宽限期
  排空或强制结束（与一元关闭语义一致）。
- 流式方法抛出异常 → 与一元一致返回 INTERNAL，连接不受影响。

## 需求（Requirements）

### 功能需求（Functional Requirements）

- **FR-001**: 系统 MUST 识别方法声明中的流式语义（请求侧流、响应侧流
  两种维度），并支持全部四种调用形态中的其余三种：服务端流、客户端
  流、双向流；一元形态行为保持不变。
- **FR-002**: 服务端 MUST 支持实现服务端流式方法：接收一条请求，按
  顺序产出零或多条强类型响应消息，以 OK 或错误状态结束。
- **FR-003**: 服务端 MUST 支持实现客户端流式方法：按序逐条读取零或
  多条强类型请求消息，感知客户端发送完毕（半关闭），返回一条响应。
- **FR-004**: 服务端 MUST 支持实现双向流式方法：同一调用上收发两个
  独立的消息序列，两侧可分别独立收尾。
- **FR-005**: 客户端 MUST 提供流式调用能力：逐条发送消息、声明发送
  完毕（半关闭）、逐条接收消息、感知流结束与终止状态、主动取消。
- **FR-006**: 线上语义 MUST 与 gRPC 流式调用兼容：同一 HTTP/2 流上
  按序传输的长度前缀消息帧序列、半关闭（END_STREAM）语义、trailers
  结束状态、gRPC 状态码；禁止引入不兼容的私有扩展。
- **FR-007**: 流内消息 MUST 按发送顺序投递，不丢失、不重复；单条
  消息大小上限沿用既有可配置上限及默认值。
- **FR-008**: 流控/背压 MUST 遵循 HTTP/2 流控语义：接收方消费不及时
  时发送方暂停投递，内存占用 MUST 有界，不随消息总数无界增长。
- **FR-009**: 客户端 MUST 能随时取消在途流式调用（CANCELLED）；服务
  端处理器 MUST 能提前以非 OK 状态终止流；取消后框架停止向对端投递
  后续消息并释放资源。
- **FR-010**: 截止时间/超时 MUST 覆盖流式调用全程（自发起到流结束），
  语义与一元一致（含超时传播）。
- **FR-011**: 对未注册流式方法的调用 MUST 返回 UNIMPLEMENTED；服务端
  处理器异常 MUST 返回 INTERNAL——两种行为与既有形态一致。
- **FR-012**: 代码生成 MUST 为三种流式形态生成与既有类型化接口形态
  一致的服务端接口方法与客户端调用入口，消息保持强类型；一元方法的
  既有生成结果 MUST 保持向后兼容。
- **FR-013**: 三种流式形态 MUST 与官方 gRPC 实现双向互通（官方对端
  作为客户端与服务端各验一轮）。
- **FR-014**: 本特性 MUST 附带三层自动化验证：组件级单元测试
  （GoogleTest）、端到端集成测试、与官方 gRPC 的流式互操作测试；
  并新增流式性能基准（Google Benchmark）纳入基准体系。
- **FR-015**: 本特性全部能力 MUST 在全部受支持平台（Linux、macOS、
  Windows）构建并通过上述验证。
- **FR-016**: 服务端优雅关闭 MUST 排空在途流式调用：停止接收新调用，
  在途流完成或超过宽限期后强制结束并释放资源（与一元关闭语义一致）。

### 关键实体（Key Entities）

- **流式调用（Streaming Call）**：一次在单条连接流上进行的「多消息
  会话」，具有方向形态（服务端流/客户端流/双向流）、生命周期状态
  （活跃/半关闭/已结束）、结束原因（正常/错误/取消/超时）；一元调用
  是其单消息特例。
- **读端（Reader）**：调用一方按序逐条接收对端消息的入口，能感知
  流结束（正常/错误）。
- **写端（Writer）**：调用一方按序逐条向对端发送消息的入口，能声明
  本侧发送完毕（半关闭）；双向流中读写两端并存且相互独立。
- **方法形态（Method Form）**：方法声明中请求/响应两侧是否为流的
  组合标注，是代码生成为服务端接口与客户端入口选择签名的依据。

## 成功标准（Success Criteria）

### 可度量结果（Measurable Outcomes）

- **SC-001**: 三种流式形态各传输 1,000 条消息的端到端验证中，消息
  数量、内容与顺序完全一致，零丢失、零重复、零错乱。
- **SC-002**: 与官方 gRPC 实现的流式互通验证全部通过（两个方向 ×
  三种形态），消息序列与结束状态符合 gRPC 语义。
- **SC-003**: 流式基准同机连续多轮运行，吞吐与时延波动不超过 30%，
  结果留档可跨版本对比。
- **SC-004**: 单流传输 10,000 条消息期间，框架内存占用保持有界
  （不随已传输消息总数线性增长）；慢消费场景下发送侧内存同样有界。
- **SC-005**: 开发者按流式示例可在 30 分钟内完成「实现一个流式方法 +
  客户端调用」并跑通端到端；实现一个流式方法的业务代码量与一元方法
  相当（不含业务逻辑本身不超过 20 行胶水代码）。
- **SC-006**: 全部新增验证（单元/集成/互操作/基准）在三个受支持平台
  的 CI 上全绿；既有一元与类型化接口测试零回归。

## 假设（Assumptions）

- 双向流包含在本特性范围内：用户点名 client/server 两类流，双向流
  是二者的组合且为 gRPC 四形态的最后缺口；若需裁剪范围，US3（双向流）
  可独立降级延后，不影响 US1/US2 交付。
- 流式调用的元数据、消息大小上限、截止时间传播、未注册方法与异常
  行为均沿用既有（一元）语义，不在本特性内重新定义。
- 与官方 gRPC 的互操作对端沿用既有决策：官方 gRPC Python 包编写的
  对端测试脚本。
- 流式服务端处理器的生命周期长于一元（跨多次消息投递），处理器模型
  以「框架逐消息驱动、不阻塞事件循环」为准绳；具体签名与交互形态
  在计划阶段设计。
- 性能治理以一元为主基准场景；本特性为流式建立基线，不设定绝对吞吐
  目标（硬件相关），以可重复、可对比为准。
